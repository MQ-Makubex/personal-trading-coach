# Prioritize the evidence core for mode workbench v1

The first version of the mode-validation workbench will reimplement four patterns inspected in the pinned Vibe-Trading source: a criterion-driven research goal, a durable proposition lifecycle, a reproducible validation run card, and a fail-closed evidence publication audit. It will live on a standalone new page and will not embed into or rearrange the existing home, modes, timeline, or other pages in v1; the only permitted change to existing pages is one shared-navigation entry labelled “模式验证”. Its first screen is risk-first: invalidated dependencies, audit failures, review-required items, first-review items, and evidence-collection work appear in that order before metrics or run history. A mode, version, and task selector establishes the page context, followed by five tabs: task overview, propositions, evidence, validation runs, and review history. Local and deployed variants retain the same structure; local-only writes appear in their relevant tabs while the deployed page renders the same areas read-only. The local workbench may run only preregistered validators selected by stable id and fixed parameter schema. It previews every run before confirmation and never accepts arbitrary commands, script paths, or natural-language code execution. V1 exposes two user-facing validators: historical-cycle replay over existing storylines, decision events, trade facts, and contemporaneous market evidence; and forward-decision observation over post-confirmation events. Historical replay proposes the complete eligible candidate set while hiding final PnL, exit outcome, and retrospective commentary; the user confirms inclusion or records exclusions before the sample list is frozen and outcomes are revealed. Old cases that cannot be blinded may only pass with warning. Forward observation registers every new decision event inside the observation window as a candidate. The user must qualify or exclude it with a reason before the preregistered deadline using only contemporaneous information; overdue events remain visible as qualification-missing and later outcomes cannot rewrite eligibility. The sample protocol defaults after-close daily candidates to a qualification deadline before the next trading-day open and intraday candidates to a deadline before the same-day close. A deadline may be tightened before formal observation begins, but it cannot be extended after the first candidate is registered; late backfills remain warning-only and do not erase qualification-missing. A deterministic backtest interface may be reserved, but it is not enabled until a mode has a complete machine-decidable rule contract. It will validate already-defined personal trading modes and will not include trade-journal behavior diagnostics or Shadow Account-style candidate-rule extraction; those discovery capabilities are deferred to a later version so that inferred patterns cannot outrun the evidence and review model that must govern them. Each mode version may have only one active validation task at a time. Starting another task supersedes, but never overwrites or deletes, the previous task and its evidence; tasks for different modes or versions may remain active concurrently. Every task freezes the referenced mode definition and hash at creation. A same-version definition drift blocks further formal evidence; the changed definition requires a new mode version and task, while the old snapshot remains auditable. The system may draft propositions and acceptance criteria from an existing mode's environment, trigger, execution-boundary, and invalidation fields, but only explicit user confirmation in the local visual workbench promotes a draft into a proposition that may receive evidence. Every confirmed proposition must also preregister at least one executable falsifier stating what evidence would weaken or overturn it; propositions without falsifiers remain drafts or background context. A proposition's operational workflow state is separate from its human review verdict: the system may advance draft, evidence-collection, review-ready, closed, or superseded states, while only the user may record pending, supported, opposed, mixed-evidence, or insufficient-evidence verdicts. Neither workflow completion nor an individual verdict automatically changes the parent mode's status. Human review writes are immutable append-only events: changing a verdict appends a new event that references the event it supersedes, while the workbench derives the current verdict from the latest valid event and preserves the full decision history. If a run or evidence item supporting the current review is invalidated, the projection becomes review-required and the proposition returns to review-ready; the historical verdict remains unchanged, and the system never substitutes a new verdict. After every required proposition is reviewed, the user performs a separate append-only whole-mode review and chooses continue-validating, replicable, avoid, or revise-as-new-version. The system may summarize proposition verdicts, counterevidence, limitations, and invalidated dependencies, but cannot vote, average, or infer the mode-level decision. Validation run cards are immutable audit records: an erroneous run is invalidated with a reason and replaced by a newly identified run, never edited or overwritten, so every review remains traceable to the exact evidence originally presented. Every run preregisters and hashes its sample inclusion rules, exclusion rules, time range, and control definition. Any post-result protocol change invalidates that run and creates a new run; both remain visible so the effect of sample selection cannot be hidden. Exploratory runs may revise propositions, parameters, and sample rules but never satisfy required criteria. Formal validation starts under a new run id after the mode snapshot and sample protocol are frozen; exploratory results cannot be promoted in place. Formal runs are never retried automatically after failure, cancellation, or service interruption. The original run keeps its terminal status, logs, and partial artifacts; any retry requires explicit confirmation and a new run id. Each formal run must include evidence independent from the mode-building process: out-of-sample periods or symbols for deterministic backtests, unseen cases for historical replay, or post-confirmation decision events for forward observation. Without an independent evidence segment, a result can only pass with warning and cannot satisfy a required criterion by itself. Evidence publication audits have three outcomes: pass evidence may be displayed and satisfy required criteria; pass-with-warning evidence must expose its sample, freshness, or method limitation and cannot satisfy a required criterion by itself; failed evidence remains research-side only. Invalidated runs, hash mismatches, missing sources, unbound propositions, missing falsifiers, non-finite metrics, mode-definition hash drift, and exploratory evidence presented as formal fail closed.
